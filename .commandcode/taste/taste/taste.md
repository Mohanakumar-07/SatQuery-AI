# Taste
- Scopes work with hard, explicit boundaries and expects them respected literally: when delegating a layer ("develop only the backend and routes"), simultaneously names what is off-limits (the models, the main pipeline, the frontend) because those parts are owned by them or another teammate. Do not scaffold, stub-in logic, or refactor outside the named scope; ask or flag a boundary case rather than quietly crossing it. Confidence: 0.85
- Works in a split-ownership team project, so deliverables should leave clean seams for the other owner (contracts / interfaces / stubs that fail loudly) instead of filling in their part. Confidence: 0.7
- Plans in advance in a written, versioned spec document kept in the repo (e.g. `Implementation_Plan_v1.2.md`) and has it open when delegating; new work is expected to conform to that document rather than to an improvised design. Confidence: 0.6
- During long multi-part builds, periodically asks for a markdown status doc committed in the repo (e.g. `BACKEND.md`) that separates *what is built* from *what is pending*, states the scope boundary of the current pass, and lists what has actually been verified vs. not. Wants this as a file, not a chat recap — and later double-checks that the file itself was actually created ("have u created the md file"), so deliverables must land as real, verifiable repo files, confirmed with a directory/file listing rather than asserted. Confidence: 0.75
- Interruptions reset momentum: a terse halt ("stop building just create md file") means abandon the running build queue immediately, produce only the named artifact, then explicitly confirm nothing else was touched and wait for a go-ahead before resuming — do not treat an in-flight todo list as permission to keep coding. Confidence: 0.8
- Writes short, informal, typo-heavy instructions ("backed", "donot") and expects the intent to be inferred and acted on rather than clarified. A bare "just <X>" ("just add git ignore", "just create md file") is a hard scope limiter: make that one change and nothing else — no accompanying refactor, no resuming the build queue, no extra files. Confidence: 0.8
- Cares strongly about VCS hygiene in a project: asks for a `.gitignore` unprompted by build work, and expects it to cover local-only stuff broadly (any virtualenv variant such as `.venv-ml/`, `__pycache__/`, caches, local SQLite/`var/`, uploaded imagery, model weights) while config templates like `.env.example` and `requirements*.txt` stay tracked. Treats the repo as source-only: downloaded weights/checkpoints and training datasets (multi-GB `.zip`/`.pt`, satellite scene tiles, GIS layers) must never enter git history, and for a working folder they will say so in absolute terms ("keep the ml folder, no other data inside it must be pushed") — meaning keep the directory and its code/manifests, ignore everything data-shaped within it. Confidence: 0.85
- Uses a bare "continue" to mean "keep going with the current plan, no recap and no questions"; wants momentum over check-ins. Confidence: 0.65
- Develops on Windows (paths like `E:\...`, `cmd`-style shell usage), so shell commands and paths must assume Windows tooling. Confidence: 0.7
